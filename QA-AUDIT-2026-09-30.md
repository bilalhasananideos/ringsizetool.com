## 2. Detailed bug reports

### Bug #1
**Title:** Privacy policy denies Cloudflare Web Analytics, but the Cloudflare RUM beacon is injected on every page
**Severity:** High — not a functional break, but a false statement in a legal document on every
visit, on a site that intends to apply for AdSense. Cheapest fix on this list.
**Status:** Confirmed Bug
**Page / URL:** every URL in the sitemap; the claim is on https://ringsizetool.com/privacy
**Component:** Cloudflare Pages project settings / Privacy page
**Environment:** any browser; also visible in raw `curl` output
**Steps to Reproduce:**
1. `curl -s https://ringsizetool.com/ | grep -o 'cloudflareinsights[^>]*'`
2. Open any page with DevTools → Network.
3. Read `/privacy` → "Analytics".
**Input Used:** none
**Expected Result:** either no Cloudflare beacon, or a privacy policy that discloses it.
**Actual Result:** all 9 pages carry
`<script src='https://static.cloudflareinsights.com/beacon.min.js' data-cf-beacon='{"token": "25b8cd59…"}'>`
and the browser POSTs to `/cdn-cgi/rum` (204). The privacy page says: "It is the only measurement
script here — there is no Cloudflare Web Analytics and no other tracker."
**Evidence:** beacon present in the served HTML of all 9 pages; `grep` of `src/` and `dist/` finds
no `cloudflareinsights` → it is injected at the Cloudflare edge, i.e. Web Analytics is switched on
in the dashboard, not in the code. Network log: `POST https://ringsizetool.com/cdn-cgi/rum → 204`.
**Root Cause:** Web Analytics enabled on the Pages project (or the zone) in the Cloudflare dashboard.
**Suggested Fix:** Cloudflare dashboard → Workers & Pages → `ringsizetool` → Metrics → Web Analytics
→ disable (or Analytics & Logs → Web Analytics → the site → disable automatic setup). Re-check with
the `curl` in step 1. If you would rather keep it, rewrite the privacy paragraph instead — Cloudflare
Web Analytics is cookieless, so only the "no other tracker" sentence is false.
**Confidence:** High

### Bug #2
**Title:** A comma decimal is silently dropped: `17,35` becomes `1735` and the tool reports US 15¾
**Severity:** High — wrong result, no warning, for a realistic input from the markets the site
explicitly serves (France, Italy, Spain, Switzerland, Brazil write decimals with a comma).
**Status:** Confirmed Bug (in Chromium with an English locale; comma-locale browsers not tested — see P5)
**Page / URL:** https://ringsizetool.com/ (and `/how-to-measure-ring-size-at-home`)
**Component:** `RingSizer.astro` — `<input id="ring-num" type="number">`
**Environment:** Desktop Chromium, `navigator.language = en-GB`, 1280 px
**Steps to Reproduce:**
1. Open the homepage, focus the exact-value field (diameter, mm).
2. Select all, type `17,35` with the keyboard.
3. Press Enter.
**Input Used:** `17,35`
**Expected Result:** US 7 (17.35 mm), or a clear "use a full stop" message.
**Actual Result:** while typing, field value = `1735` (Chrome drops the comma in a number input),
readout = 24.35 mm, **US 15¾ / UK Z+6 / EU 76**. After Enter the field is rewritten to `24.35`. No
hint appears (1735 is not a plausible circumference either).
**Evidence:** live: `{num:"1735", main:"24.35", us:"15¾", badInput:false}`.
**Root Cause:** `type="number"` rejects the non-locale separator without flagging `badInput`, and
the value then falls into Bug #3's silent clamp.
**Suggested Fix:** use `type="text" inputmode="decimal"` with a small parser that accepts `,` or `.`
(`value.replace(',', '.')`), rejects anything else, and shares Bug #3's out-of-range message. The
calibration field `#cal-num` has the same pattern and should get the same treatment.
**Confidence:** High

### Bug #3
**Title:** Out-of-range typed values are silently clamped and presented as a confident size
**Severity:** Medium
**Status:** Confirmed Bug
**Page / URL:** https://ringsizetool.com/
**Component:** `RingSizer.astro` — `handleValueChange` / `showUnitHint`
**Environment:** Desktop Chromium 1280 px (behaviour is viewport-independent)
**Steps to Reproduce:**
1. Diameter + mm. Type `11.63` (US 0 by the site's own FAQ) and press Enter.
2. Repeat with `12.5`, `0`, `-1`, `0.001`, `1.5`, `10.999`, `25`, `999999`, `1e5`.
**Input Used:** listed above
**Expected Result:** what the homepage promises — "where a scale does not define a size, this tool
prints an em dash instead of inventing one" — or at least a message that the value was outside the
supported 12.90–24.34 mm range.
**Actual Result:** every low value → field rewritten to `12.89`, **US 1½ / UK C½ / EU 41 / JP 1**;
every high value → `24.35`, **US 15¾ / UK Z+6 / EU 76 / JP 35**. No message. The only warning path
(the circumference/diameter hint) fires only when the number fits the *other* measure.
**Evidence:** live input sweep (24 values). Contradictions: FAQ "What is 10 mm in ring size?" says
"US 0, which starts at 11.63 mm"; typing 11.63 shows US 1½. Homepage `#about-tool` promises an em
dash; no em dash is reachable from the UI.
**Root Cause:** `currentDia = Math.min(DIA_MAX, Math.max(DIA_MIN, …))` with no user-facing
feedback unless `fits` is true.
**Suggested Fix:** in `showUnitHint`, when `didClamp && !fits`, show the status line with
"`X` mm is outside what this tool can size (12.90–24.34 mm) — showing the nearest size it can." Or
render em dashes in the result grid until a valid value is entered. Add a `verify-sizes.ts`
assertion that the clamp path produces a message.
**Confidence:** High

### Bug #4
**Title:** The wrong-measure hint is never cleared on mode/unit/source change; acting on it can give US 15¾
**Severity:** Medium
**Status:** Confirmed Bug
**Page / URL:** https://ringsizetool.com/
**Component:** `RingSizer.astro` — `unitHint`, `setMode`, `setSource`, `unitHintSwitch` click handler
**Environment:** Desktop Chromium 1280 px
**Steps to Reproduce (A — button):**
1. Diameter + mm, type `51.87` (a US 6 circumference), Enter → hint appears (correct).
2. Click the **Inches** unit pill → the hint stays, still saying "51.87 mm…".
3. Click **Use it as circumference**.
**Steps to Reproduce (B — pill):**
1. Diameter + mm, type `51.87`, Enter → hint appears.
2. Do what it asks by clicking the **Circumference** pill instead of the hint's button.
**Input Used:** `51.87`
**Expected Result:** A: hint hidden once the unit changes, or the value converted. B: 51.87 mm
circumference → US 6.
**Actual Result:** A: mode becomes circumference-inches, field shows `51.87`, readout `3.0114 in`,
result **US 15¾** — field and readout disagree. B: the tool shows **76.49 mm circumference → US
15¾** (the clamped diameter carried over, the typed 51.87 is gone) and the stale hint is still on
screen; it also survives source changes ("A ring that fits", "Just my finger").
**Evidence:** live state dumps (`afterUnitSwitch_hintStillShown`, `afterHintClick`,
`afterManualCircPill`).
**Root Cause:** `unitHint.hidden` is only reset inside `showUnitHint`, which runs only from a
committed value change; the typed value is discarded at the clamp and the button replays a bare
number in whatever unit is now active.
**Suggested Fix:** hide the hint at the top of `setMode()` and `setSource()`; store the typed
value's unit alongside it (`dataset.unit`) and convert in the click handler; when the user flips
measure manually while the hint is showing, re-apply the typed value rather than the clamped one.
**Confidence:** High

### Bug #5
**Title:** "Reset" stores the default guess and labels the screen "✓ Actual size on your screen"
**Severity:** Medium — the site's one claim ("calibrated to your screen") is displayed for a screen
that was never calibrated, and the calibration drawer is then skipped on every return visit.
**Status:** Confirmed Bug (documented in code as a deliberate "known edge"; still a UI claim the
behaviour does not back)
**Page / URL:** https://ringsizetool.com/
**Component:** `RingSizer.astro` — `[data-cal-reset]` handler
**Environment:** Desktop Chromium 1280 px, fresh localStorage
**Steps to Reproduce:**
1. Fresh visit: marker reads "Not calibrated yet".
2. In the drawer, click **Reset**.
3. Reload the page.
**Expected Result:** Reset returns to the uncalibrated state (no stored value, "Not calibrated yet").
**Actual Result:** marker "✓ Actual size on your screen", ruler "Calibrated to this screen.",
`localStorage['rst.pxPerMm'] = 3.7795…`, `rst.dprAtCalibration = 1`; after reload the drawer is
hidden. Worked example on a 4.12 px/mm laptop: a 16.51 mm (US 6) ring matched on a circle drawn at

`removeItem(DPR_STORE_KEY)`, apply `startingPpm()`, and call `setCalibrated(false)`.
**Confidence:** High

### Bug #6
**Title:** Japanese sizes are attributed to JIS S 4700 with a range and rule that standard does not contain
**Severity:** Medium — the numbers are right, the citation is not, and "every number traces to a
cited standard" is the site's differentiator.
**Status:** Confirmed Bug (content / citation)
**Page / URL:** `/` (3 places), `/ring-size-chart`, `/about`, `/printable-ring-sizer`,
`/average-ring-size`, FAQ "What is US size 7 in Japan?", `/llms.txt`
**Component:** content — `src/data/faq.ts:196`, `src/pages/index.astro:317,465,524`,
`ring-size-chart.astro:325`, `about.astro:44`, `printable-ring-sizer.astro:343`,
`average-ring-size.astro:166`, `public/llms.txt:18`, comments in `src/data/ringSizes.ts`
**Environment:** n/a
**Steps to Reproduce:** read the FAQ answer: "Japan uses JIS S 4700, which runs from 1 to 35 and
steps by a third of a millimetre of diameter".
**Expected Result:** a citation that matches the source.
**Actual Result:** JIS S 4700 defines ring size as the **inner circumference in millimetres,
41–76, rounded to the nearest mm and displayed as the ISO 8653 number** — the same scale as EU.
The 1号 = 13.0 mm diameter, +⅓ mm scale the site uses is the traditional Japanese 号 convention
(called JCS by Japanese retailers), which is what most Japanese shops actually label rings with.
**Evidence:**
- JIS S 4700:1998 text (kikakurui.com): 「指輪のサイズ　指輪の内周を，ミリメートルで表した数値」;
  gauge range 最小 41 / 最大 76; display rounded to nearest mm, e.g. "ISO 8653-43".
- Three Japanese retailers describe the 2022 edition as based on ISO 8653:2016 (inner
  circumference, e.g. "54"), and distinguish it from JCS 号 (1号 = 13.0 mm / 40.8 mm).
- The site's **values** match the 号 scale exactly: Maverick Store table 1号 40.8, 9号 49.2,
  13号 53.4, 20号 60.7 mm circumference = π × (13 + (n−1)/3) to 0.1 mm.
**Root Cause:** the scale was attributed to the JIS number without reading the JIS text — the same
failure mode the France note in `ringSizes.ts` warns about.
**Suggested Fix:** relabel as "Japan (号)" and cite "the traditional Japanese 号 scale (JCS):
1号 = 13 mm inner diameter, +⅓ mm per size. The Japanese Industrial Standard itself (JIS S 4700)
uses the ISO circumference number — the EU column." Drop "runs 1 to 35" as a JIS claim (keep
`JP_MAX` as an evidence-based cap, like `INDIA_MAX`). Add the 4 retailer points above as
`verify-sizes.ts` assertions. Owner should read the revised wording before it ships.
**Confidence:** High for the 1998 text; Medium-High that the 2022 revision is unchanged in this
respect (paywalled; three independent Japanese sources agree).

### Bug #7
**Title:** Chart "Circ. inches" column is printed at 3 dp; two rows give a different size when typed back
**Severity:** Low
**Status:** Confirmed Bug
**Page / URL:** https://ringsizetool.com/ring-size-chart → tool in circumference + inches
**Component:** `ring-size-chart.astro:155` (`circumferenceIn.toFixed(3)`); the tool's own

**Expected Result:** the chart row's sizes (JP 23; UK Y).

format with the same helper the chart uses and drop the `> 13` exclusion.
**Confidence:** High

## 6. Source code findings

- `verify-sizes.ts` round-trip loop tests the tool's precision, not the chart's printed precision,
  and skips rows above US 13 (root cause of #7).
- Reset writing a stored value is documented as a deliberate "known edge" (`RingSizer.astro:1110`)
  → #5.

## 9. Potential issues (need verification)

- **P1 — Printable sheet forces A4.** `@page { size: A4 portrait }` while the FAQ says the sheet
  works on A4 or Letter "as long as the paper… matches". On a Letter-default setup the browser lays

  it. Needs a real Letter print preview.

  the uncalibrated circle is ~45% too large. The marker honestly says "Not calibrated".
